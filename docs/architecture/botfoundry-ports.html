Os Ports — Interfaces C#

ISessionStore
Driven Port
Defines where and how each user's session is persisted between messages.
ISessionStore.cs Abstractions 
public interface ISessionStore
{
    Task<UserSession?> GetAsync(
        long chatId,
        CancellationToken ct = default);

    Task SaveAsync(
        UserSession session,
        CancellationToken ct = default);

    Task DeleteAsync(
        long chatId,
        CancellationToken ct = default);
}
Implementations
InMemorySessionStore
provided by the library default 
// BotFoundry.Telegram/Adapters/
// Registered automatically in DI
// if no other is registered (ADR-002)
internal class InMemorySessionStore : ISessionStore { ... }
RedisSessionStore
implemented by the consumer optional 
// In the bot project — register before AddBotFoundry
services.AddSingleton<ISessionStore, RedisSessionStore>();
Concept — ADR-002
The library registers InMemorySessionStore as a fallback through the DI convention. If the consumer has already registered another ISessionStore, the fallback is ignored — the consumer's choice is never overwritten.
IMessageSender
Driven Port
Abstracts sending replies to the user, isolating the Telegram.Bot SDK from the core.
IMessageSender.cs Abstractions 
public interface IMessageSender
{
    Task SendTextAsync(
        long chatId,
        string text,
        CancellationToken ct = default);

    Task SendTextAsync(
        long chatId,
        string text,
        ReplyMarkup? markup,
        CancellationToken ct = default);
}
Implementations
TelegramMessageSender
provided by the library production 
// The ONLY place that uses the Telegram.Bot SDK
// BotFoundry.Telegram/Adapters/ (ADR-003)
internal class TelegramMessageSender : IMessageSender { ... }
FakeMessageSender
created in the tests tests 
// Core.Tests — no Telegram, no network
public class FakeMessageSender : IMessageSender
{
    public List<string> SentMessages { get; } = [];
}
Concept — ADR-003
O SDK Telegram.Bot is referenced only in TelegramMessageSender. The core calls IMessageSender — it does not know Telegram exists. In tests, FakeMessageSender collects the messages without opening a connection.
ITopicHandler
Driven Port — Domain
Contract the consumer implements to answer a specific command (/start, /help…).
ITopicHandler.cs Abstractions 
public interface ITopicHandler
{
    /// Command this handler serves, e.g. "start"
    string Command { get; }

    Task<FlowResult> HandleAsync(
        BotContext context,
        CancellationToken ct = default);
}
Example — implementation by the consumer
StartHandler in the bot project 
public class StartHandler : ITopicHandler
{
    public string Command => "start";

    public async Task<FlowResult> HandleAsync(
        BotContext ctx, CancellationToken ct)
    {
        await ctx.SendAsync("Hello! What is your name?", ct);
        return FlowResult.Continue();
    }
}
Concept — Domain Port
The library does not know StartHandler — it calls ITopicHandler. The consumer registers the handlers through DI and the Routing discovers them at runtime. The core never needs to be modified to support new commands.
IConversationStep
Driven Port — Domain
Defines one step of a multi-step flow: what to ask, how to validate and how to process the reply.
IConversationStep.cs Abstractions 
public interface IConversationStep
{
    string StepId { get; }

    /// Sends the question to the user
    Task AskAsync(
        BotContext context,
        CancellationToken ct = default);

    /// Validates the user's reply
    Task<bool> ValidateAsync(
        BotContext context,
        CancellationToken ct = default);

    /// Processes and decides the next step
    Task<StepResult> ProcessAsync(
        BotContext context,
        CancellationToken ct = default);
}
Concept — StepRunner (Fluxo 2)
The core's StepRunner invokes ValidateAsync → ProcessAsync in a loop. StepResult can be Continue, Complete or JumpTo(stepId) — the consumer decides the flow; the core runs the mechanics.
IAuthMiddleware
Driven Port — Optional
Decides whether a user is allowed to continue in the pipeline. Optional — if not registered, every user gets through.
IAuthMiddleware.cs Abstractions 
public interface IAuthMiddleware
{
    Task<bool> IsAllowedAsync(
        BotContext context,
        CancellationToken ct = default);
}
Example — admin list
AdminOnlyMiddleware in the bot project 
public class AdminOnlyMiddleware : IAuthMiddleware
{
    private readonly long[] _admins = [123456, 654321];

    public Task<bool> IsAllowedAsync(
        BotContext ctx, CancellationToken ct)
        => Task.FromResult(_admins.Contains(ctx.ChatId));
}
Concept — Optional Port
The core checks IAuthMiddleware whether it was registered. Otherwise, it skips the check. The library never forces authentication — it exposes the hook and the consumer decides the rule.
ILlmBridge
Driven Port — Extension
Forwards free-text messages (with no active command) to an external language agent.
ILlmBridge.cs Abstractions 
public interface ILlmBridge
{
    Task<string> ProcessAsync(
        string userMessage,
        BotContext context,
        CancellationToken ct = default);
}
Concept — Extension Point (Flow 3)
When the Routing finds no command and no active flow, it checks whether ILlmBridge was registered. If so, it forwards the message. The actual integration with OpenAI, Gemini or another agent is 100% the consumer's responsibility.

Supporting Models

BotContext
Agnostic Model
Object that travels through the pipeline, carrying the message and the user's session. It contains no SDK types.
BotContext.cs Abstractions 
public sealed class BotContext
{
    public long        ChatId    { get; init; }
    public string      Text      { get; init; }
    public UserSession Session   { get; init; }
    public IMessageSender Sender { get; init; }

    // Shortcut for the consumer to send replies
    public Task SendAsync(string text, CancellationToken ct = default)
        => Sender.SendTextAsync(ChatId, text, ct);
}
Concept — Boundary Model
BotContext is created by TelegramPollingAdapter from the SDK object, but carries no SDK type. It is the "translation" from the outside world to the library's internal vocabulary.
UserSession
State Model
User state persisted between messages — active topic, current step and conversation data.
UserSession.cs Abstractions 
public sealed class UserSession
{
    public long    ChatId       { get; set; }
    public string? ActiveTopic  { get; set; }
    public string? ActiveStepId { get; set; }
    public DateTimeOffset ExpiresAt { get; set; }

    public Dictionary<string, string> Data { get; }
        = new();

    public bool IsExpired
        => DateTimeOffset.UtcNow > ExpiresAt;
}

Dependency Rules

Violations of these rules indicate an architectural error — the core can never "look outside".

REGRA 01
Core depends only on Abstractions
BotFoundry.Telegram.Core references only BotFoundry.Telegram.Abstractions. It never references Telegram.Bot nor the adapters project.
REGRA 02
SDK stays in a single adapter
Only TelegramMessageSender and TelegramPollingAdapter can use using Telegram.Bot. The rest of the library is agnostic (ADR-003).
REGRA 03
Abstractions has no dependencies
The Abstractions project does not reference any other project in the library. It is the core of the dependency graph — everyone depends on it, it depends on no one.
REGRA 04
The consumer does not access the Core
The bot developer references only Abstractions to implement their handlers and steps. Never accesses internal types of the Core directly.
