C# Code

Ports/ISessionStore.cs
Driven Port
Defines where and how each user's session is persisted between messages. The library registers InMemorySessionStore automatically if no implementation was registered before (ADR-002).
namespace BotFoundry.Telegram.Abstractions.Ports;

public interface ISessionStore
{
    Task<UserSession?> GetAsync(
        long chatId,
        CancellationToken ct = default);

    Task SaveAsync(
        UserSession session,
        CancellationToken ct = default);

    Task DeleteAsync(
        long chatId,
        CancellationToken ct = default);
}
Concept — ADR-002
The core calls ISessionStore without knowing whether the session lives in memory, Redis or a database. Swapping the implementation is a DI registration matter — zero change in the Core.
Ports/IMessageSender.cs
Driven Port
Abstracts sending replies to the user. It is the core's only contact point with the outgoing outside world — the Telegram.Bot SDK never appears in the Core.
namespace BotFoundry.Telegram.Abstractions.Ports;

public interface IMessageSender
{
    Task SendTextAsync(
        long chatId,
        string text,
        CancellationToken ct = default);

    Task SendTextAsync(
        long chatId,
        string text,
        IReadOnlyList<string>? quickReplies,
        CancellationToken ct = default);
}
Concept — ADR-003
Only TelegramMessageSender (adapters project) implements this interface using the SDK. In tests, a FakeMessageSender collects the messages in memory — no network, no token.
Ports/ITopicHandler.cs
Domain Port
Contract the consumer implements to answer a specific command (/start, /help…). The library invokes this contract when Routing identifies the command.
namespace BotFoundry.Telegram.Abstractions.Ports;

public interface ITopicHandler
{
    /// Command this handler serves (without "/"), e.g. "start"
    string Command { get; }

    Task<FlowResult> HandleAsync(
        BotContext context,
        CancellationToken ct = default);
}
Concept — Zone 2 (Domain)
The library never knows the bot's business logic — it only knows the contract. The consumer registers N handlers through DI; Routing finds which one to invoke at runtime by the value of Command.
Ports/IConversationStep.cs
Domain Port
Defines one step of a multi-step flow — what to ask, how to validate and how to process the user's reply.
namespace BotFoundry.Telegram.Abstractions.Ports;

public interface IConversationStep
{
    /// Unique identifier of the step within the flow
    string StepId { get; }

    /// Sends the question to the user
    Task AskAsync(
        BotContext context,
        CancellationToken ct = default);

    /// Validates the received reply — returns false to repeat the question
    Task<bool> ValidateAsync(
        BotContext context,
        CancellationToken ct = default);

    /// Processes the valid reply and decides the next step
    Task<StepResult> ProcessAsync(
        BotContext context,
        CancellationToken ct = default);
}
Concept — StepRunner (Flow 2)
The Core's StepRunner calls ValidateAsync → ProcessAsync on every message. StepResult returns Continue, Complete or JumpTo — the consumer controls the flow; the core runs the mechanics.
Ports/IAuthMiddleware.cs
Optional Port
Decides whether a user is allowed to continue in the pipeline. If not registered in DI, the pipeline skips the check and every user gets through.
namespace BotFoundry.Telegram.Abstractions.Ports;

public interface IAuthMiddleware
{
    Task<bool> IsAllowedAsync(
        BotContext context,
        CancellationToken ct = default);
}
Concept — Optional Hook
The library does not impose access rules — it exposes the hook. The consumer decides whether to implement it (admin list, JWT token, etc.). If not registered, the pipeline proceeds without a check.
Ports/ILlmBridge.cs
Extension Port
Forwards free-text messages (with no active command) to an external language agent. Activated only in Flow 3 — when there is no command and no active step.
namespace BotFoundry.Telegram.Abstractions.Ports;

public interface ILlmBridge
{
    Task<string> ProcessAsync(
        string userMessage,
        BotContext context,
        CancellationToken ct = default);
}
Concept — Extension (Flow 3)
The actual integration with OpenAI, Gemini or another LLM is 100% the consumer's responsibility. The library only checks whether the port was registered and, if so, delegates the message.
Models/BotContext.cs
Boundary Model
Object created by TelegramPollingAdapter from the SDK object and injected into the pipeline. It contains no Telegram.Bot type — it is the "translation" from the outside world to the library's internal vocabulary.
namespace BotFoundry.Telegram.Abstractions.Models;

public sealed class BotContext
{
    public required long           ChatId   { get; init; }
    public required string         Text     { get; init; }
    public required UserSession    Session  { get; init; }
    public required IMessageSender Sender   { get; init; }

    /// Shortcut for the consumer to send replies without accessing Sender directly
    public Task SendAsync(
        string text,
        CancellationToken ct = default)
        => Sender.SendTextAsync(ChatId, text, ct);

    public Task SendAsync(
        string text,
        IReadOnlyList<string> quickReplies,
        CancellationToken ct = default)
        => Sender.SendTextAsync(ChatId, text, quickReplies, ct);
}
Concept — Boundary Model
BotContext is the input contract of every domain Port. The consumer receives a BotContext in their handlers — never SDK objects. This guarantees the bot's code is testable without Telegram.
Models/UserSession.cs
State Model
User state persisted between messages — which flow is active, which step it is on and data collected throughout the conversation.
namespace BotFoundry.Telegram.Abstractions.Models;

public sealed class UserSession
{
    public required long ChatId { get; init; }

    /// Command of the active flow, e.g. "signup". Null if no flow is active.
    public string? ActiveTopic  { get; set; }

    /// StepId of the current step within the active flow.
    public string? ActiveStepId { get; set; }

    public DateTimeOffset ExpiresAt { get; set; }

    /// Data collected during the conversation (free key per step)
    public Dictionary<string, string> Data { get; }
        = new();

    public bool IsExpired
        => DateTimeOffset.UtcNow > ExpiresAt;

    public bool HasActiveFlow
        => ActiveTopic is not null;

    public void ClearFlow()
    {
        ActiveTopic  = null;
        ActiveStepId = null;
        Data.Clear();
    }
}
Models/FlowResult.cs
Result Model
Return of ITopicHandler.HandleAsync — tells the pipeline whether the flow should keep waiting for input or finished in the same message.
namespace BotFoundry.Telegram.Abstractions.Models;

public sealed class FlowResult
{
    public bool IsComplete { get; private set; }

    /// Flow started — waits for the user's next message
    public static FlowResult Continue()
        => new() { IsComplete = false };

    /// Flow ended in the same message — no active step
    public static FlowResult Complete()
        => new() { IsComplete = true };
}
Concept — Static Factory Methods
The FlowResult.Continue() and FlowResult.Complete() pattern makes the consumer's code expressive and self-documenting — it is immediately readable what the handler is signaling to the pipeline.
Models/StepResult.cs
Result Model
Return of IConversationStep.ProcessAsync — instructs the StepRunner on what to do after processing the user's input.
namespace BotFoundry.Telegram.Abstractions.Models;

public sealed class StepResult
{
    public StepResultKind Kind     { get; private set; }
    public string?        TargetId { get; private set; }

    /// Advances to the next step in sequence
    public static StepResult Continue()
        => new() { Kind = StepResultKind.Continue };

    /// Ends the flow — clears the session state
    public static StepResult Complete()
        => new() { Kind = StepResultKind.Complete };

    /// Redirects to a specific step by StepId
    public static StepResult JumpTo(string stepId)
        => new() { Kind = StepResultKind.JumpTo, TargetId = stepId };
}

public enum StepResultKind
{
    Continue,
    Complete,
    JumpTo
}
Concept — JumpTo and conditional branching
JumpTo is the branching mechanism of the multi-step flow. The consumer can redirect to any step by StepId — the StepRunner does not need to know the branching logic, it just runs the destination.

How the Models Relate

BotContext → IMessageSender
BotContext exposes SendAsync as a shortcut, delegating to IMessageSender. The consumer never needs to inject IMessageSender directly into their handler.
BotContext → UserSession
The session is always available in context.Session. A step can store data in Session.Data["name"] = value and read it in the following steps.
ITopicHandler → FlowResult
The handler returns FlowResult.Continue() if it started a multi-step flow or FlowResult.Complete() if it replied and finished everything in the same message.
IConversationStep → StepResult
Each step returns Continue, Complete or JumpTo(stepId). The StepRunner uses these values to advance, end or redirect the flow.
